# telegram-broadcast

Актуальная версия: **0.2.0**.

Асинхронная библиотека рассылок для Telegram со своей SQLite-базой. В приложение нужно передать только токен бота и путь к файлу. Библиотека создаёт каталог и таблицы, открывает и закрывает соединения, сохраняет прогресс и результаты. Токен в БД не записывается.

Python 3.11+. SQLAlchemy и aiosqlite используются внутри библиотеки; настройка `Base`, engine и сессий приложения не требуется.

## Установка

Установка напрямую из GitHub (нужны Python 3.11+ и Git):

```powershell
python -m pip install "git+https://github.com/Solarmove/telegram-broadcast.git@main"
```

## Подключение

```python
import asyncio
import os

from telegram_broadcast import BroadcastClient, BroadcastMessage

async def main() -> None:
    async with BroadcastClient(
        os.environ["TELEGRAM_BOT_TOKEN"],
        database_path="data/broadcasts.sqlite3",
    ) as broadcasts:
        broadcast_id = await broadcasts.create(
            BroadcastMessage("<b>Новая акция!</b>"),
            recipient_ids=[123456789, 987654321],
            notification_chats=[123456789, -1001234567890],
            title="Акция октября",
        )
        print("ID рассылки:", broadcast_id)
        result = await broadcasts.run(broadcast_id)
        print(result.status, result.success, result.failed, result.unknown)

        result = await broadcasts.get_result(broadcast_id)
        deliveries = await broadcasts.get_deliveries(broadcast_id, limit=100, offset=0)
        for delivery in deliveries:
            print(delivery.chat_id, delivery.status, delivery.error)


if __name__ == "__main__":
    asyncio.run(main())
```

По умолчанию файл называется `broadcasts.sqlite3` в текущем рабочем каталоге. Можно передать `str` или `pathlib.Path`; путь преобразуется в абсолютный при создании клиента. Для постоянного размещения лучше указать абсолютный путь. Библиотека использует файловую SQLite, а не `:memory:` или URL подключения.

`create()` возвращает UUID и сохраняет снимок получателей. Дубликаты ID удаляются; отправка выполняется по возрастанию ID. Пустой список отклоняется. Для статистики можно передать несколько чатов или пустой список. Эти чаты независимы от получателей рассылки.

`run()` запускается явно и возвращает `BroadcastResult`. Фоновые задачи контролирует приложение. Например, можно вызвать `asyncio.create_task(broadcasts.run(broadcast_id))`, сохранив задачу для ожидания и обработки исключений. Клиент должен оставаться открытым до завершения всех задач.

Пример полного скрипта: [examples/basic.py](examples/basic.py). Перед запуском задайте `TELEGRAM_BOT_TOKEN` и замените ID.

## Сообщения и настройки

`BroadcastMessage` принимает текст, необязательный объект `BroadcastMedia` и `parse_mode`. HTML включён по умолчанию; для обычного текста задайте `parse_mode=None`, для MarkdownV2 — `parse_mode="MarkdownV2"`. Текст обязателен, если не задано медиа. Ограничение — 4096 символов для текста и 1024 для подписи к медиа.

Медиа задаётся типом aiogram `ContentType` и ровно одним источником: `file_id`, HTTP(S) `url` или локальный `path_to_file`. Поддерживаются фото, видео, документ, аудио, анимация, voice, video note и sticker. Telegram file ID, полученный при первой отправке, сохраняется и повторно используется для следующих получателей.

```python
from aiogram.enums import ContentType
from telegram_broadcast import BroadcastMedia, BroadcastMessage

message = BroadcastMessage(
    text="Новое предложение",
    media=BroadcastMedia(
        content_type=ContentType.PHOTO,
        url="https://example.org/photo.jpg",
    ),
    parse_mode=None,
)
```

Для локального файла укажите `path_to_file="/path/to/photo.jpg"`; файл должен оставаться доступным при возобновлении рассылки. Для уже загруженного файла передайте `file_id="..."`. Для отчётов в Telegram-топик передайте `NotificationRecipient(chat_id, thread_id=...)` в `notification_chats`. Обычный ID чата также принимается как сокращённая форма.

Параметр `policy` конструктора принимает `RunPolicy`. Все интервалы задаются в секундах:

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `send_interval` | `0.05` | Пауза после попытки отправки |
| `report_interval` | `5` | Интервал обновления статистики |
| `network_retry_delay` | `5` | Пауза перед следующей отправкой после сетевого сбоя |
| `control_poll_interval` | `0.5` | Интервал проверки паузы и отмены во время ожидания |

```python
import os

from telegram_broadcast import BroadcastClient, RunPolicy

client = BroadcastClient(
    os.environ["TELEGRAM_BOT_TOKEN"],
    database_path="data/broadcasts.sqlite3",
    policy=RunPolicy(send_interval=0.1, report_interval=15),
)
```

Перед использованием такого клиента войдите в `async with client` либо после работы вызовите `await client.close()` внутри своей асинхронной функции.

## Жизненный цикл и хранение

Вход в `async with` создаёт файл и таблицы при необходимости. Можно использовать клиент без контекстного менеджера: первый вызов операции с БД выполнит инициализацию; после завершения работы обязательно вызовите `await broadcasts.close()`. Закрытый клиент повторно использовать нельзя — создайте новый с тем же путём.

Библиотека владеет соединениями SQLite и собственной Telegram-сессией. Внедрённый `transport` остаётся под управлением вызывающего кода. Выделите отдельный файл для рассылок; интеграции с БД приложения нет.

В файле хранятся четыре таблицы:

| Таблица | Содержимое |
| --- | --- |
| `tg_broadcast_jobs` | Сообщение, бот, состояние и счётчики |
| `tg_broadcast_deliveries` | Результат каждого получателя |
| `tg_broadcast_notifications` | Сообщения статистики и ошибки по каждому чату |
| `tg_broadcast_cooldowns` | Сохранённое ограничение скорости бота |

Версия схемы хранится в `PRAGMA user_version`. Текущая схема — `4`; базы схем `1`, `2` и `3` обновляются автоматически. Схема `3` сохраняет время первого запуска и завершения рассылки. Для старых записей эти поля изначально пусты: историческое время отправки восстановить нельзя. Неизвестная версия отклоняется явной ошибкой.

Используются WAL, `foreign_keys=ON`, `synchronous=FULL` и ожидание занятой SQLite до 30 секунд. Записи выполняются в коротких транзакциях; сетевые запросы не держат SQLite-транзакцию открытой. WAL позволяет читать результаты во время записи; SQLite по-прежнему допускает только одного писателя одновременно.

Создание схемы сериализуется между процессами через файл `<имя БД>.schema.lock`. Для запусков рядом создаётся каталог `<имя БД>.locks` с блокировкой каждого бота. Второй одновременный `run()` того же бота и файла БД получает `BotBusy`, даже из другого клиента или процесса. После завершения или аварийного выхода процесса ОС освобождает блокировку; оставшийся lock-файл сам по себе не означает, что бот занят.

Используйте локальный диск. Разные файлы БД не координируют отправки одного бота; совместный запуск через сетевой файловый ресурс не поддерживается. Пока клиенты работают, сохраняйте файл БД и соседние WAL/SHM/lock-файлы на своих местах. Для резервной копии закрывайте все клиенты либо используйте SQLite backup API.

## Прогресс и управление

- `get_result(id)` — состояние, счётчики, время следующей попытки, результаты уведомлений.
- `get_deliveries(id, limit=100, offset=0)` — страница результатов, включая Telegram message ID и ошибку. Максимум 1000 записей.
- `pause(id)` — остановка между отправками; текущая отправка может завершиться.
- `resume(id)` — перевод из паузы в очередь; затем снова вызовите `run(id)`.
- `cancel(id)` — прекращение оставшихся отправок.
- `run(id, wait_for_cooldown=False)` — вернуть управление при ограничении скорости. Планировщик может повторить `run()` после `result.next_retry_at`.
- `run(id, max_duration=30)` — ограничить работу между сетевыми операциями; начатый запрос к Telegram не обрывается по этому лимиту.

Состояния: `queued`, `running`, `paused`, `completed`, `cancelled`, `failed`. `completed` означает, что все получатели обработаны; проверяйте также `failed` и `unknown`. Повторный `run()` завершённой рассылки не отправляет сообщения получателям снова, но может повторить неудачный итоговый отчёт.

После перезапуска создайте клиент с тем же токеном и путём и вызовите `run(id)`. Рассылкой может управлять только клиент с тем же числовым ID бота. Это проверка принадлежности данных, не авторизация для публичного API.

Методы принимают объект `uuid.UUID`, который возвращает `create()`. Если ID сохранён строкой, преобразуйте его через `UUID(saved_id)` из модуля `uuid`.

`BroadcastResult` и результаты получателей — неизменяемые dataclass-объекты. Основные поля статистики:

| Поле | Значение |
| --- | --- |
| `total` | Количество уникальных получателей |
| `success`, `failed`, `unknown` | Подтверждённые отправки, отказы и неизвестные результаты |
| `processed` | Сумма `success + failed + unknown` |
| `remaining` | Количество ещё не обработанных получателей |
| `error` | Ошибка, остановившая рассылку, если есть |
| `next_retry_at` | Время следующей допустимой попытки в UTC либо `None` |
| `notifications` | Кортеж результатов отчётов: `chat_id`, `thread_id`, `message_id`, `error`, `updated_at` |
| `started_at`, `finished_at` | Время первого запуска и завершения; `None`, пока событие не произошло или если время не записывалось старой версией |

`get_deliveries()` возвращает кортеж `DeliveryResult`: `chat_id`, `status`, `message_id`, `error`, `updated_at`. Состояния доставки: `pending`, `sending`, `success`, `failed`, `unknown`.

## Ошибки доставки

Перед сетевым запросом коммитится `sending`. После подтверждённого ответа результат и счётчики коммитятся в одной транзакции.

| Ситуация | Поведение |
| --- | --- |
| Пользователь заблокировал бота / чат недоступен | `failed` у получателя; остальные продолжают |
| Telegram `RetryAfter` | Получатель остаётся `pending`; сохраняется общая пауза бота |
| Сетевой сбой / серверная ошибка Telegram | `unknown` у получателя; после `network_retry_delay` рассылка продолжается |
| Telegram отклонил токен / содержимое сообщения | `failed` у получателя с сохранением причины; остальные продолжают |
| Прерывание процесса во время запроса | При следующем запуске `sending` становится `unknown` |
| Ошибка БД / неожиданная программная ошибка | Исключение возвращается вызывающему коду; журнал позволяет восстановиться |

Telegram не предоставляет ключ идемпотентности отправки. При потере ответа нельзя надёжно узнать, доставлено ли сообщение. `unknown` автоматически не повторяется, чтобы избежать дублей. При сбое записи после успешного ответа результат также может стать `unknown`. Счётчик `success` отражает подтверждённые и сохранённые ответы.

Локальные проверки выполняются до отправки: неправильный формат токена отклоняется конструктором, некорректное сообщение — `BroadcastMessage`, пустые или недопустимые ID — `create()`. Ошибки проверки не создают рассылку со статусом `failed`.

После локальных проверок каждый вызов `create()` обращается к Telegram: проверяет действительность токена через `getMe`, все уникальные чаты администраторов через `getChat`, а для групп и каналов — членство бота и доступные права через `getChatMember`. При неверном токене, неизвестном чате, запрете на отправку или недоступности Telegram выбрасывается `PreflightError`; запись рассылки и получатели в БД не создаются. Ошибка содержит ID проблемных чатов и причины в `issues`. Проверка токена выполняется и при пустом `notification_chats`.

```python
from telegram_broadcast import BroadcastMessage, PreflightError

try:
    broadcast_id = await broadcasts.create(
        BroadcastMessage("test"),
        recipient_ids=[123456789],
        notification_chats=[-1001234567890],
    )
except PreflightError as error:
    print(error)  # Рассылка не создана; указан проблемный чат и ответ Telegram.
else:
    result = await broadcasts.run(broadcast_id)
```

Проверка не отправляет пробных сообщений. Существование конкретной темы форума и возможность отправки в личный чат не гарантируются запросом `getChat`; такие ошибки, как и изменившиеся после проверки права, обнаруживаются при отправке отчёта. Если указан `thread_id` в группе без тем, создание отклоняется сразу. Список `recipient_ids` массово через Telegram не проверяется: результат доставки сохраняется по каждому получателю во время запуска.

Пользовательский `BroadcastTransport` теперь должен реализовывать `async validate(notifications) -> None`: успешный возврат разрешает создание, исключение блокирует его. В стандартном aiogram-транспорте проверка обязательна и не кешируется между вызовами `create()`.

Ожидаемые ошибки публичного API: `BotBusy` при занятом боте, `BroadcastNotFound` при неизвестном UUID, `WrongBot` при чужой рассылке, `InvalidTransition` при недопустимом изменении состояния и `ConfigurationError` при ошибочной конфигурации или использовании закрытого клиента. Они наследуются от `BroadcastError` и импортируются из `telegram_broadcast`.

Уведомления статистики отправляются в начале, периодически и при завершении запуска; существующее сообщение редактируется. Ожидаемые ошибки уведомления сохраняются отдельно и не ломают доставку. `RetryAfter` уведомления приостанавливает бота. Потеря ответа при отправке первого отчёта может привести к дублирующему сообщению статистики при повторе.

Первый отчёт отправляется до первого получателя, поэтому уведомления работают и для рассылки одному пользователю. Во время `run()` отдельная задача обновляет отчёт каждые 5 секунд, в том числе во время долгого запроса отправки. Интервал задаёт `RunPolicy(report_interval=5)`; минимальный интервал ограничен `control_poll_interval`. После окончания то же сообщение заменяется итогом:

```text
Рассылка

Обработано: 1355/3323 (40.8%)
✅ Успешно: 871
❌ Ошибок: 484

⚡ Средняя: 4.98 msg/s
Текущая: 4.85 msg/s

⏱ Прошло: 272.3 сек
⏳ Осталось: ~395.5 сек
```

```text
✅ Рассылка завершена

Успешно: 950
Ошибок: 539
Обработано: 1489/1489
Успешность: 63.8%

⏱ Время: 299.9 сек
⚡ Средняя скорость: 4.96 сообщений/сек
```

Средняя скорость — число обработанных получателей, делённое на время с первого запуска. Время включает ожидания Telegram, паузы и перерывы между запусками. Текущая скорость измеряется за интервал между обновлениями; при новом запуске её первое значение — `0.00`. Оценка оставшегося времени использует среднюю скорость, а до первой обработки показывает «рассчитывается». Успешность — доля успешных среди обработанных. Если есть неизвестные результаты доставки, добавляется строка «⚠️ Неизвестно». Отмена и ошибка имеют собственные заголовки и не обозначаются как успешное завершение.

Администраторы задаются явно через `notification_chats`: библиотека не определяет их по токену. Ошибки Telegram записываются в журнал `telegram_broadcast.reporting` с уровнем WARNING и остаются доступны в `result.notifications`. Если отчёт не пришёл, выведите результат:

```python
result = await broadcasts.run(broadcast_id)
for notification in result.notifications:
    print(notification.chat_id, notification.thread_id, notification.error)
```

Пример с настройкой логирования и отчётами в группу: [examples/notifications.py](examples/notifications.py).

## Изменения версии 0.2

Удалены параметры `base`, `engine`, `session_factory`, `prefix`, `lock`, `auto_create_tables`, публичная функция `register_tables()` и метод `create_tables()`. Вместо них передаётся `database_path`; SQLite настраивается автоматически. PostgreSQL и `asyncpg` больше не требуются. Пример выше показывает новый конструктор. Данные из PostgreSQL автоматически не переносятся.

## Разработка и проверка

`client.py` — публичный API; `database.py` — SQLite и соединения; `schema.py` — собственная схема; `repository.py` — SQL; `runner.py` — выполнение и журнал; `progress.py` — расчёт скорости и времени; `reporting.py` — сообщения статистики; `validation.py` — проверка токена и админских чатов; `transport.py` — адаптер aiogram; `locking.py` — файловая блокировка; `types.py` и `errors.py` — контракт.

```powershell
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
uv build
```

Тесты хранения используют реальные временные файлы SQLite и штатную файловую блокировку; Telegram заменяется fake transport. Проверяются восстановление, повторное открытие, параллельные клиенты и освобождение блокировки после аварии отдельного процесса. CI настроен на Windows/Linux и Python 3.11/3.13.


Язык уведомлений выбирается перед рассылкой через `create()` и сохраняется в БД:

```python
job = await client.create(
    BroadcastMessage("Текст сообщения"),
    recipient_ids,
    notification_chats=[admin_chat_id],
    notification_language="uk",  # "uk" — украинский, "ru" — русский (по умолчанию)
)
await client.run(job)
```

Выбранный язык применяется к начальным, промежуточным и итоговым уведомлениям.
При остановке из-за ошибки уведомление содержит причину с удалёнными токенами.
Неожиданное исключение по-прежнему передаётся вызывающему коду; библиотека пытается
отправить отчёт об остановке, сохраняя возможность восстановления журнала.
