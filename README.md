# telegram-broadcast

Асинхронная библиотека рассылок для Telegram. Принимает токен бота, ваш SQLAlchemy `Base` и `AsyncEngine`. Получатели, прогресс, результаты и состояние уведомлений хранятся в вашей БД. Токен библиотека в БД не записывает.

Python 3.11+, SQLAlchemy 2.0, aiogram 3. PostgreSQL — рабочая БД. SQLite используется только в тестах с подменённой блокировкой. FastAPI, HTTP-сервер и отдельная БД не требуются.

## Подключение

Используйте `Base` и `engine` своего приложения. Сессии библиотеки работают в собственных коротких транзакциях: незакоммиченная сессия запроса в библиотеку не передаётся.

```python
import os

from telegram_broadcast import BroadcastClient, BroadcastMessage
from my_application.database import Base, engine

async with BroadcastClient(
    os.environ["TELEGRAM_BOT_TOKEN"], base=Base, engine=engine,
) as broadcasts:
    broadcast_id = await broadcasts.create(
        BroadcastMessage("<b>Новая акция!</b>"),
        recipient_ids=[123456789, 987654321],
        notification_chat_ids=[123456789, -1001234567890],
        title="Акция октября",
    )
    result = await broadcasts.run(broadcast_id)
    print(result.status, result.success, result.failed, result.unknown)

    result = await broadcasts.get_result(broadcast_id)
    deliveries = await broadcasts.get_deliveries(broadcast_id, limit=100, offset=0)
```

`create()` возвращает UUID и сохраняет снимок получателей. Повторяющиеся ID удаляются; отправка выполняется по возрастанию ID. Пустой список отклоняется. Получатели уведомлений независимы от получателей рассылки; можно передать несколько чатов или пустой список.

`run()` запускается явно и возвращает `BroadcastResult`. Фоновые задачи создаёт и контролирует приложение. Можно вызвать `asyncio.create_task(broadcasts.run(broadcast_id))`, сохранив задачу для ожидания и обработки исключений. Клиент должен оставаться открытым до завершения задачи.

Пример полного скрипта: [examples/basic.py](examples/basic.py). Для запуска нужны `DATABASE_URL` (например, `postgresql+asyncpg://user:password@localhost/app`) и `TELEGRAM_BOT_TOKEN`. Замените ID перед запуском.

## Таблицы и миграции

Конструктор регистрирует в `Base.metadata` четыре Core-таблицы:

| Таблица | Содержимое |
| --- | --- |
| `tg_broadcast_jobs` | Сообщение, бот, состояние и агрегированные результаты |
| `tg_broadcast_deliveries` | Результат каждого получателя |
| `tg_broadcast_notifications` | Сообщения статистики и ошибки по каждому чату |
| `tg_broadcast_cooldowns` | Сохранённое ограничение скорости бота |

Вход в `async with` создаёт только таблицы библиотеки через `create_all(checkfirst=True)`. Таблицы приложения не создаются и не изменяются. Без контекстного менеджера вызовите `await broadcasts.create_tables()` и в конце `await broadcasts.close()`.

Регистрация идемпотентна для одной пары `metadata/prefix`. Чужие таблицы с теми же именами приводят к `ConfigurationError`. Можно задать `prefix="my_broadcast"`. Поддерживается `MetaData(schema=...)`; саму PostgreSQL-схему приложение создаёт заранее.

Для production с Alembic управляйте DDL через миграции:

```python
# В Alembic env.py, до присваивания target_metadata:
from telegram_broadcast import register_tables
register_tables(Base)
target_metadata = Base.metadata

# В приложении, после применения миграции:
broadcasts = BroadcastClient(
    token, base=Base, engine=engine, auto_create_tables=False,
)
```

`create_all` не обновляет существующие таблицы. Изменения схемы требуют миграции. При автоматическом создании таблиц выполняйте первый запуск последовательно: несколько процессов могут одновременно пройти `checkfirst`.

Можно передать `session_factory=async_sessionmaker(engine, expire_on_commit=False)`. Она должна быть привязана к тому же engine. Библиотека закрывает собственную Telegram-сессию; engine и внедрённый транспорт остаются у приложения.

## Прогресс, управление и повторный запуск

- `get_result(id)` — состояние, счётчики, время следующей попытки, результаты уведомлений.
- `get_deliveries(id, limit=100, offset=0)` — страница результатов, включая Telegram message ID и ошибку. Максимум 1000 записей.
- `pause(id)` — остановка между отправками; текущая отправка может завершиться.
- `resume(id)` — перевод из паузы в очередь; затем снова вызовите `run(id)`.
- `cancel(id)` — прекращение оставшихся отправок.
- `run(id, wait_for_cooldown=False)` — вернуть управление при ограничении скорости. Планировщик может повторить `run()` после `result.next_retry_at`.
- `run(id, max_duration=30)` — ограничить работу между сетевыми операциями; начатый запрос к Telegram не обрывается по этому лимиту.

Состояния: `queued`, `running`, `paused`, `completed`, `cancelled`, `failed`. `completed` означает, что все получатели обработаны; проверяйте также `failed` и `unknown`. Повторный `run()` завершённой рассылки не отправляет сообщения получателям повторно, но может повторить неудачный итоговый отчёт.

В PostgreSQL отдельное соединение удерживает advisory transaction lock на ID бота на время `run()`. Коммиты журнала не освобождают блокировку. Второй `run()` этого бота получает `BotBusy`, в том числе для другой рассылки. Пул должен предоставлять как минимум два соединения: для блокировки и для коротких транзакций. Координация действует между процессами, использующими одну PostgreSQL БД; разные БД не координируются.

После перезапуска создайте клиент с тем же токеном, Base, engine и prefix и вызовите `run(id)`. Рассылкой может управлять только клиент с тем же числовым ID бота. Это проверка принадлежности данных, не авторизация для публичного API.

## Ошибки доставки

Перед сетевым запросом коммитится `sending`. После подтверждённого ответа результат и счётчики коммитятся в одной транзакции.

| Ситуация | Поведение |
| --- | --- |
| Пользователь заблокировал бота / чат недоступен | `failed` у получателя; остальные продолжают |
| Telegram `RetryAfter` | Получатель остаётся `pending`; сохраняется общая пауза бота |
| Сетевой сбой / серверная ошибка Telegram | `unknown`; запуск прекращается, остальные остаются для следующего `run()` |
| Некорректный токен / сообщение | Рассылка становится `failed`; остаток не отправляется |
| Прерывание процесса во время запроса | При следующем запуске `sending` становится `unknown` |
| Ошибка БД / неожиданная программная ошибка | Исключение возвращается вызывающему коду; журнал позволяет восстановиться |

Telegram не предоставляет ключ идемпотентности отправки. При потере ответа нельзя надёжно узнать, было ли сообщение доставлено. `unknown` автоматически не повторяется, чтобы избежать дублей. При сбое записи после успешного ответа результат также может стать `unknown`. Счётчик `success` отражает подтверждённые и сохранённые ответы.

Уведомления статистики отправляются в начале, периодически и при завершении запуска; существующее сообщение редактируется. Ожидаемые ошибки уведомления сохраняются отдельно и не ломают доставку. `RetryAfter` уведомления также приостанавливает бота. Потеря ответа при отправке первого отчёта может привести к дублирующему сообщению статистики при повторе.

`RunPolicy` настраивает интервалы отправки, отчётов, повторного запуска после сетевого сбоя и проверки управления. HTML включён по умолчанию; для обычного текста задайте `parse_mode=None`. Поддерживаются текст, фото и видео по HTTP(S) URL; полученный Telegram file ID используется для следующих получателей этой рассылки. Ссылки должны быть доступны Telegram. Локальные файлы, альбомы и клавиатуры в этой версии не поддерживаются.

## Архитектура и проверка

`client.py` — публичный API и жизненный цикл; `schema.py` — таблицы; `repository.py` — SQL; `runner.py` — выполнение и журнал; `reporting.py` — статистика; `transport.py` — адаптер aiogram; `locking.py` — блокировка PostgreSQL; `types.py` и `errors.py` — контракт.

```powershell
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest
uv build
```

SQLite-тесты используют fake Telegram transport и тестовую блокировку; реальных сообщений не отправляют. Для интеграционных проверок задайте `TELEGRAM_BROADCAST_TEST_DSN` на отдельную PostgreSQL БД и запустите `uv run pytest -m postgres`. Тесты создают и удаляют только собственные таблицы со случайным префиксом. GitHub Actions настроен на Python 3.11/3.13 и PostgreSQL 16.
